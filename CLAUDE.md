# Clydeford Habits — Product & Technical Specification

**Working title:** "Clydeford Habits" is a placeholder — final name TBD. Hosted on `clydeford.net` as a **standalone product**, deliberately separate from the Foundry brand. Nothing below depends on the final name.

**Version:** 0.1 draft · July 2026
**Builder:** Claude Code
**Owner:** Steven

---

## 1. What we're building (plain English)

A mobile-first Progressive Web App that helps people build good habits using the mechanics from *Atomic Habits*: start tiny, attach new habits to existing routines, protect streaks, and frame habits around identity ("I'm someone who trains") rather than outcomes ("lose 10kg").

The app ships with a library of several hundred pre-written habits across all areas of life. An AI-powered interview learns who the user is and what they want, and a fast rules engine picks the right handful of habits to surface each day. Users adopt habits, check them off, build streaks, and stack habits into routines.

It is a **product**, not a personal tool: multi-user, sign-ups, built from day one to scale on Cloudflare's free/cheap tiers.

> **Control plane vs data plane.** The architecture splits cleanly the way a router does. The AI (Claude API) is the *control plane*: it runs occasionally, thinks slowly, and updates the user's "routing table" — their profile. The rules engine is the *data plane*: every app open, it forwards traffic fast using that table, with zero AI cost. AI never sits in the hot path.

## 2. Product principles (the Atomic Habits mechanics)

These are not decoration — they shape the data model and UI, and Claude Code should treat them as requirements:

1. **Tiny by default.** Every habit in the library has a *tiny version* (≤2 minutes: "put on your running shoes"), a *standard version* ("run 15 minutes"), and optionally an *ambitious version*. New adopters always start on tiny.
2. **Habit stacking.** Habits attach to anchors: "After I pour my morning coffee, I will …". The library suggests anchor types; users build their own stacks.
3. **Identity framing.** Every habit carries an identity statement shown at adoption and on streak milestones: "You're becoming someone who reads every day."
4. **Never miss twice.** A streak survives one missed day *if* the next day is completed — shown as a "streak repair" rather than a reset to zero. Missing two consecutive days breaks the streak.
5. **Make it obvious, easy, satisfying.** Suggestions match the user's time of day and available minutes; check-off is one tap; completion gives immediate satisfying feedback (animation, streak counter tick).
6. **Progression, not overload.** Users hold a small number of active habits (default cap 5, user-adjustable). The engine suggests graduating tiny → standard only after a stable streak.

## 3. Users & accounts

- **Sign-up/sign-in: passwordless magic links.** User enters their email, receives a one-time login link, clicks it, gets a session. No passwords to store or breach.
  > Like out-of-band verification: instead of trusting a secret the user recites, we prove they control the channel (their inbox).
- Sessions: HttpOnly secure cookie referencing a `sessions` row in D1. 30-day rolling expiry.
- Email delivery via **Resend** (or MailChannels — see Open Decisions §15). API key stored as a Worker secret.
- Passkeys (Face ID / fingerprint login) are a Phase 3 upgrade, not MVP.
- Only PII collected: email address and a display name. No date of birth, no health data fields.

## 4. The habit library

**Target: 350–500 habits at launch**, generated by Claude Code at build time as seed data, reviewed by Steven, loaded into D1, and versioned so it can be extended without touching user data.

**Categories (~12, roughly 30–40 habits each):**
Exercise & Movement · Nutrition & Hydration · Sleep & Rest · Mental Health & Mindfulness · Home & Housework · Money & Admin · Relationships & Social · Work & Focus · Learning & Growth · Digital Hygiene · Outdoors & Nature · Health & Self-care

**Each habit record contains:**

| Field | Example |
|---|---|
| `title` | "Read before bed" |
| `category` / `tags` | Learning & Growth / `reading`, `evening`, `wind-down` |
| `identity_statement` | "I'm someone who reads every day" |
| `tiny_version` | "Read one page" |
| `standard_version` | "Read for 15 minutes" |
| `ambitious_version` | "Read for 30 minutes" |
| `cue_suggestion` | "After I get into bed…" |
| `time_of_day` | `evening` (morning / midday / evening / anytime) |
| `duration_minutes` | 15 |
| `difficulty` | 1–3 |
| `frequency_default` | daily (or weekly ×N for things like meal prep) |
| `stack_anchors` | suggested anchor types ("with morning coffee", "after brushing teeth") |
| `prerequisites` | free text, e.g. "needs running shoes" (most habits: none) |

Habits must be written to be **safe and universal**: no medical claims, no diet prescriptions, no assumptions about ability. Phrasing stays encouraging and concrete.

## 5. Profile & Q&A engine (the AI part)

**Onboarding interview (first run):** a short conversational session (8–12 questions) powered by the Claude API, server-side. It feels like a chat: "What does a typical weekday morning look like?", "Which area of life feels most neglected right now?", with tappable quick-replies plus free text.

**Recurring check-ins:** every ~2 weeks (and on demand), a shorter 3–5 question session: what's working, what's stalled, what's changed.

**Output is structured, not vibes.** The AI's job ends with writing a JSON profile that a schema validates before it's stored:

```json
{
  "category_scores": {"exercise": 80, "housework": 35, ...},
  "capacity_minutes_per_day": 30,
  "preferred_times": ["morning", "evening"],
  "identity_goals": ["healthier", "more organised"],
  "avoid_tags": ["running"],
  "notes": "shift worker, mornings vary"
}
```

If the AI returns malformed JSON, the Worker retries once, then falls back to defaults — the app never breaks because a model had a bad day.

**Implementation notes for Claude Code:**
- All Claude API calls happen in the Worker (never from the browser); the API key is a Worker secret.
- Use a small, cheap model (Haiku-class) with a tight system prompt and a hard token budget per session.
- Cost envelope: an onboarding session should cost well under a penny per user. Log token usage per session to a `qa_sessions` table so costs are observable.
- Rate limit: max 3 AI sessions per user per day.

## 6. Daily suggestion engine (the rules part)

Runs on every app open (and powers notification content). **Pure deterministic scoring — no AI, no cost, explainable.** Same philosophy as Bastion: deterministic, auditable decisions.

Each candidate habit gets a score:

```
score = w1·category_fit        (profile score for its category)
      + w2·time_match          (habit's time_of_day vs now)
      + w3·capacity_fit        (duration fits user's available minutes)
      + w4·balance_bonus       (boost under-represented categories)
      + w5·novelty             (not suggested in last 14 days)
      + w6·progression         (right difficulty for streak maturity)
      − declined_penalty       (user dismissed it before)
      − adopted_exclusion      (already active → excluded)
```

Weights live in one config file so they can be tuned without code changes. Top 3 scores become today's suggestions. Every suggestion and its outcome (adopted / dismissed / ignored) is logged to `suggestion_log` — that log is the tuning data for Phase 3.

> This is a routing policy: metrics in, best next-hop out, same inputs always give the same answer. When something surprising is suggested, you can read the score breakdown and see exactly why — no black box.

## 7. Tracking: check-ins, streaks, stacks, stats

- **Check-off:** one tap per habit per day (or per scheduled day for weekly habits). Undo allowed same-day.
- **Streaks:** current and best streak per habit, with the never-miss-twice repair rule from §2. Milestones celebrated at 7 / 30 / 66 / 100 days (66 = the research-backed average to automaticity — a nice teaching moment in-app).
- **Stacks:** users chain habits into named routines ("Morning routine: coffee → stretch → journal"). The UI presents a stack as one card with sequential check-offs.
- **Stats (Phase 2):** completion rate per habit and category, streak history, weekly heatmap (GitHub-contribution style), "identity progress" summaries.
- All timestamps stored UTC; each user stores an IANA timezone (e.g. `Europe/London`) captured at onboarding, so "today" and streak boundaries are computed in *their* day, not the server's.

## 8. Notifications

- **Web Push (VAPID)** — the standards-based push that PWAs use. VAPID keypair stored as Worker secrets; subscriptions stored per-device in `push_subscriptions`.
- **iOS caveat:** iPhones only allow push after the PWA is added to the home screen. Onboarding must therefore include a friendly install prompt flow ("Add to Home Screen to get reminders") with per-platform instructions.
- **Scheduling:** a Cloudflare **Cron Trigger** runs every 15 minutes, finds users whose local reminder time falls in that window, and sends their daily nudge (today's suggestions or due habits).
  > Push is an SNMP trap, not polling: the server tells the phone when something matters, instead of the app waking up to ask.
- User controls: reminder time(s), quiet hours, per-habit reminders on/off, global mute. Default: one gentle daily nudge, nothing more — notification fatigue kills habit apps.

---

## 9. PWA behaviour & offline

- Installable: web manifest (icons, theme colour, standalone display), service worker via **vite-plugin-pwa**.
- **Offline-first for the daily loop:** today's habits and suggestions are cached locally; check-offs made offline are queued and synced when connectivity returns (last-write-wins is fine at this scale).
  > Store-and-forward: like a branch router queueing syslog during a WAN outage and flushing when the link recovers. The user on a train can still tick off their habits.
- The AI Q&A requires connectivity (clearly indicated); everything else works offline.

## 10. Visual design & delight

The app should look and feel **cartoonish, fun, and uplifting** — closer to Duolingo than to a corporate wellness dashboard. This is a requirement, not garnish: in a habit app, delight *is* the reward loop ("make it satisfying", §2).

**Art direction:**
- Bold, saturated palette on a light background; each of the 12 categories gets its own accent colour.
- Chunky rounded shapes everywhere: big tap targets, pill buttons, cards with fat corner radii and soft "sticker" shadows.
- A rounded display typeface for headings (e.g. Baloo 2 or Nunito, self-hosted); a clean sans for body text.
- Playful flat illustrations or emoji-scale icons per habit category. Optionally a reactive **mascot** (see Open Decisions §15).

**Motion & effects:**
- Check-off: squash-and-stretch button press, animated tick, confetti burst (canvas-confetti — a tiny library), and a short haptic buzz via the Vibration API on phones that support it.
- Streaks: an animated flame/counter that levels up visually with milestone tiers; milestone days (7/30/66/100) trigger a full-screen celebration.
- Streak repair: a "phew — saved it!" moment. Warm and funny, never shaming.
- Micro-interactions on everything: cards spring in, tabs bounce, the daily suggestions deal out like playing cards.

**Guardrails (so fun doesn't cost us):**
- All motion CSS/spring-based, 60fps on a mid-range phone; canvas-confetti is the only animation library allowed.
- Respect `prefers-reduced-motion` — every effect needs a calm fallback for users who've asked their phone for less movement.
- Sound effects optional and **off by default**.
- Tone of voice: warm, playful, encouraging — never guilt. A broken streak gets "Fresh start!", not red warnings.

## 11. Architecture & stack

| Layer | Choice | Why |
|---|---|---|
| Hosting/API | Cloudflare **Worker** (Hono framework) | Same platform as vault/Bastion; one deployable unit |
| Database | **D1** (SQLite) | Relational fits this data; already proven in vault |
| Frontend | **React + Vite + Tailwind**, served as Worker static assets | Mainstream = easiest for Claude Code to build and maintain well |
| PWA | vite-plugin-pwa | Generates manifest + service worker correctly |
| Scheduled jobs | Cron Triggers | Push sending, streak maintenance, cleanup |
| AI | Claude API (Haiku-class), Worker-side only | §5 |
| Email | Resend (decision pending) | Magic links |
| Secrets | Worker secrets | Claude API key, VAPID keys, Resend key |

Single repo, single `wrangler` deploy. Environments: `dev` (workers.dev URL) and `production` (custom domain).

## 12. Data model (D1 tables)

- `users` — id, email, display_name, timezone, created_at
- `sessions` — token hash, user_id, expires_at
- `magic_links` — token hash, email, expires_at, used_at
- `habits` — the library (§4 fields), `library_version`
- `profiles` — user_id, JSON profile (§5), updated_at
- `user_habits` — user_id, habit_id, level (tiny/standard/ambitious), custom cue, stack_id, position, adopted_at, archived_at
- `stacks` — user_id, name
- `checkins` — user_habit_id, local_date, completed_at (unique per habit per local day)
- `streaks` — user_habit_id, current, best, last_completed_date, repair_available (denormalised for fast reads)
- `qa_sessions` — user_id, type (onboarding/checkin), transcript JSON, tokens_used, created_at
- `suggestion_log` — user_id, habit_id, score, score_breakdown JSON, shown_at, outcome
- `push_subscriptions` — user_id, endpoint, keys, platform, created_at

Every user-owned table is scoped by `user_id` and **every query filters on the session's user_id** — the multi-tenancy rule. Like VRFs: tenants share the hardware but their route tables never bleed into each other.

## 13. Security & privacy

- Magic link tokens: single-use, 15-minute expiry, stored hashed.
- Rate limiting on auth endpoints and AI endpoints (per-IP and per-user).
- UK/GDPR basics from day one: **export my data** (JSON download) and **delete my account** (hard delete, cascading) as self-service settings. Privacy policy page noting that Q&A text is processed via the Claude API.
- Deliberately minimal data: no health metrics, no location, no analytics SDKs at MVP. Habit data is personal; collect nothing we don't use.
- Standard headers: HSTS, CSP, no third-party scripts.

## 14. Build phases

**Phase 1 — MVP (build first, end-to-end):**
Auth (magic links) → habit library seeded → onboarding AI interview → profile stored → daily rule-based suggestions → adopt/dismiss → one-tap check-off → basic streaks with repair rule → installable PWA with offline check-off → mobile UI polished in the §10 cartoon style, with check-off effects in from day one.

**Phase 2:**
Web Push + Cron reminders (with iOS install-prompt flow) → stats dashboard & heatmap → habit stacking UI → fortnightly AI check-ins → tiny→standard graduation prompts.

**Phase 3 (product-ready):**
Passkeys → admin view (library management, cost/usage dashboards) → suggestion-weight tuning from `suggestion_log` → billing (Stripe, free tier + paid) → custom user-created habits.

Definition of done for Phase 1: a stranger can sign up on their phone, be interviewed, get sensible suggestions, adopt three habits, and hold a streak for a week — without ever seeing an error.
